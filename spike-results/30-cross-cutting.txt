Task 6: Cross-cutting checks — JDK stability, reproducible builds, uberjar
============================================================================

Method note: this task does NOT diff against the historical 10-bnd-bundle-modules.txt
or 20-moditect-all-modules.txt captures. Task 5's Experiment A permanently installed a
moditect-built kubernetes-model-common (carrying a real module-info.class) into ~/.m2.
Any module depending on it now resolves a named module where the historical captures
saw an unnameable 999-SNAPSHOT jar. Diffing a fresh build against those older files
would attribute ~/.m2 drift to the build JDK and produce a false positive. Instead,
each arm below was captured on JDK 17 and JDK 11 back to back in this session, and
those two captures were diffed against each other — isolating the build JDK as the
only changed variable.

Question 3: is kubernetes-openshift-uberjar correctly left without a descriptor by
BOTH arms? (spec edge case 3)
=====================================================================================

--- bnd arm ---

  $ git checkout spike/jpms-bnd
  Switched to branch 'spike/jpms-bnd'

  $ ./scripts/mvnj -pl uberjar clean package -DskipTests 2>&1 | tee /tmp/uberjar-bnd-build.log | tail -10
  [WARNING] otherwise try to manually exclude artifacts based on
  [WARNING] mvn dependency:tree -Ddetail=true and the above output.
  [WARNING] See https://maven.apache.org/plugins/maven-shade-plugin/
  [INFO] Attaching shaded artifact.
  [INFO] ------------------------------------------------------------------------
  [INFO] BUILD SUCCESS
  [INFO] ------------------------------------------------------------------------
  [INFO] Total time:  19.694 s
  [INFO] Finished at: 2026-08-09T08:30:05+01:00
  [INFO] ------------------------------------------------------------------------

  $ ./scripts/dump-module-descriptors.sh uberjar/target/kubernetes-openshift-uberjar-999-SNAPSHOT.jar
  === kubernetes-openshift-uberjar-999-SNAPSHOT.jar ===
  NO module-info.class (automatic module)
  Unable to derive module descriptor for: uberjar/target/kubernetes-openshift-uberjar-999-SNAPSHOT.jar
  kubernetes.openshift.uberjar.999.SNAPSHOT: Invalid module name: '999' is not a Java identifier

  Result for bnd: NO module-info.class, as expected (matching the brief's expected
  output exactly). Investigated WHY: the Felix maven-bundle-plugin (which carries bnd's
  JPMSModuleInfoPlugin) only binds to Maven's lifecycle for packaging=bundle.
  uberjar/pom.xml declares packaging=jar, so the bundle plugin's mojo never executes at
  all —

  $ /usr/bin/grep "bundle\|moditect" /tmp/uberjar-bnd-build.log
  (no output — confirmed no bundle-plugin or moditect-plugin goal ran during this build;
  this shell's bare `grep` is wrapped by an rtk token-optimization hook that prepends
  line numbers even without -n, so /usr/bin/grep was used directly here to avoid any
  doubt about whether the wrapper could also suppress or alter a true negative — it
  cannot: a real absence of matches is exit 1, no output, on both the wrapped and
  unwrapped binary)

  This means bnd's "exclusion" of the uberjar is INCIDENTAL, a side effect of
  packaging=jar never entering the bundle lifecycle — not an explicit skip.

  570:[ERROR] Failed to execute goal org.moditect:moditect-maven-plugin:1.3.0.Final:add-module-info (add-module-info) on project kubernetes-openshift-uberjar: Execution add-module-info of goal org.moditect:moditect-maven-plugin:1.3.0.Final:add-module-info failed: No assignedModuleName provided for jar with invalid module name: /home/austek/.m2/repository/io/fabric8/kubernetes-model-core/999-SNAPSHOT/kubernetes-model-core-999-SNAPSHOT.jar -> [Help 1]

  (line numbers above are prefixed by this shell's `grep` wrapper — an rtk
  token-optimization hook per CLAUDE.md — even though -n was not passed; they are the
  real source line numbers from the log, not something added by hand)

  DEFECT FOUND, moditect arm: the build FAILS OUTRIGHT (exit 1) — it does not merely
  skip the descriptor. moditect-maven-plugin's add-module-info execution is bound
  directly in the root pom's <build><plugins> (line ~1430), unconditionally, with no
  packaging guard and no per-module exclusion for kubernetes-openshift-uberjar (checked
  uberjar/pom.xml directly — no <skip> or plugin override there). So moditect DOES
  attempt to process the shaded/relocated uberjar; it only fails to complete because one
  of the uberjar's declared dependencies (kubernetes-model-core, resolved from ~/.m2 for
  this single-module `-pl uberjar` build) does not carry a real module-info and its
  version string ("999-SNAPSHOT") cannot form a legal automatic module name either. This
  is the same "999-SNAPSHOT can't auto-name" failure mode documented for other modules
  in Task 5, now hitting the uberjar via its dependency closure.

  This means: unlike the bnd arm, moditect's non-interference with the uberjar is NOT
  structural — it happens to fail via this dependency-resolution error before it would
  otherwise have gone on to try to synthesize and write a descriptor onto a jar that
  shades and relocates every model package. If that one dependency's module name were
  resolvable, there is no visible guard in the moditect execution config (no
  <assignedModuleName> for kubernetes-openshift-uberjar's own artifact, no exclusion
  entry naming it) that would stop moditect from writing a module-info onto the
  uberjar itself. The exclusion this arm needs is not explicit; it is presently working
  only by accident, and the accident manifests as a build failure, not a clean skip.

  The shade step itself (which runs before the moditect step in the package phase)
  still produces a shaded jar on disk before the build aborts:

  $ ./scripts/dump-module-descriptors.sh uberjar/target/kubernetes-openshift-uberjar-999-SNAPSHOT.jar
  === kubernetes-openshift-uberjar-999-SNAPSHOT.jar ===
  NO module-info.class (automatic module)
  Unable to derive module descriptor for: uberjar/target/kubernetes-openshift-uberjar-999-SNAPSHOT.jar
  kubernetes.openshift.uberjar.999.SNAPSHOT: Invalid module name: '999' is not a Java identifier

  Identical output to the bnd arm's uberjar dump above — same "999" automatic-module
  naming failure, since both arms' shade configuration is defined once in
  uberjar/pom.xml, unaffected by which arm is checked out.

  So the artifact that exists on disk after a failed moditect-arm build has no
  descriptor either, matching the bnd arm's result — but the overall `mvn package`
  invocation for this module fails on this arm, which the bnd arm's does not. A CI
  pipeline building the moditect arm end-to-end would need either a fix to the
  dependency's module-naming problem or an explicit exclusion added for this module —
  today it has neither.

  All 6 of kubernetes-model-core's exported packages are duplicated, unrelocated, inside

  package against kubernetes-model-core (and against every other model module it
  shades). This is the concrete evidence for why the uberjar can never be a valid named
  module under either mechanism.

Question 3 overall answer: bnd correctly leaves the uberjar without a descriptor, but
only because packaging=jar structurally keeps it out of the OSGi bundle lifecycle — the
exclusion is incidental, not a deliberate skip. moditect's build for this module FAILS
outright rather than cleanly skipping; the artifact that ends up on disk has no
descriptor, but only because an unrelated dependency-naming defect aborts the build
before moditect gets a chance to try. Neither arm has an explicit, intentional exclusion
for kubernetes-openshift-uberjar today; both rely on incidental behavior, and the
moditect arm's incidental behavior is a hard build failure, which is more fragile than
the bnd arm's silent no-op.

Summary
=======
1. JDK stability (11 vs 17): both arms produce byte-identical descriptor content for
   the modules that build successfully. Build failures are consistent across JDKs
   within each arm (same modules, same causes) and were already characterized in Tasks
   2 and 5 — they are not JDK-induced. JDK 21 was not exercised by this task.
2. Reproducibility: REPRODUCIBLE. bnd's descriptor-carrying zjsonpatch jar builds
   byte-identical across two independent invocations; no reproducibility regression
   from adding module-info.class.
3. Uberjar: both arms leave kubernetes-openshift-uberjar without a module-info.class in
   the artifact that ends up on disk, but neither does so by deliberate design — bnd's
   omission is a structural consequence of packaging=jar, and moditect's build for this
   module fails outright due to an unrelated dependency-naming defect before it would
   otherwise attempt to write one. Split-package scanning confirms why a descriptor
   would be wrong if either mechanism ever succeeded in writing one: all 6 of
   kubernetes-model-core's packages are duplicated, unrelocated, inside the uberjar.

Scope reminder: this task and Task 4 show that descriptors/provides clauses are
generated; neither proves ServiceLoader resolves them at runtime from a real module
path. That is Phase 6 / verification-layer-2 work, out of scope here.
