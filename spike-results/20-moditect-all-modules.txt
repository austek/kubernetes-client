IMPORTANT CAVEAT: this result does not actually test "does moditect honour osgi.export" — see
"Edge case findings" below. Both openshift-model's and openshift-model-config's builds failed
before moditect ever ran jdeps on them (neither jar has a module descriptor, real or automatic),
so no exports clause was ever generated by moditect for either jar to check against the
exclusion. What scan-split-packages.sh actually measured here is that the two jars' RAW CLASS
FILES never physically overlapped in the first place:

  $ unzip -l kubernetes-model-generator/openshift-model/target/openshift-model-999-SNAPSHOT.jar | grep -c "api/model/config"
  0

openshift-model.jar contains zero io.fabric8.openshift.api.model.config.* class files. The split
risk the bnd arm's Step 6 fix addressed was specific to BND'S WILDCARD Export-Package pattern
("io.fabric8.openshift.api.model**", a double-wildcard that matches the config.* sub-package
declaratively even though no such classes are physically present) — a bnd-specific
over-claiming risk, not a literal JPMS split package. jdeps computes `exports` strictly from
packages it can see class files for in the target jar; it has no equivalent wildcarded
declarative Export-Package syntax that could over-claim a namespace. So this specific species of
risk is structurally inapplicable to the jdeps-based mechanism — not because moditect "honours"
osgi.export (it does not read it at all, confirmed: osgi.export is bnd/OSGi-only metadata), but
because jdeps never had a mechanism to make the mistake bnd's wildcard could make. Whether
moditect would honour a REAL split package (two jars both physically containing the identical
package) remains untested here, because no such real physical split exists between these two
modules to test against.

=============================================================

HEADLINE FINDING — directly contradicts the brief's anticipated central advantage:

Only 1 of 7 modules (zjsonpatch) produced a real module descriptor. The other 6 all failed with
BUILD FAILURE, every one on the identical root cause: jdeps requires every jar it places on its
module path — not just the 7 modules in scope for this task, but the ENTIRE transitive
dependency closure, including non-target reactor siblings — to resolve to a legal automatic
module name. This project's dependencies in this reactor are all versioned "999-SNAPSHOT" (this
is the actual current dev version on main, not a spike artifact — see pom.xml line 26). The JPMS
automatic-module-name algorithm's version-stripping regex only recognizes a purely numeric
dotted-decimal version suffix; "999-SNAPSHOT" is not purely numeric (the "-SNAPSHOT" tail is not
digits), so the regex anchor fails, no stripping happens, and "999" and "SNAPSHOT" leak into the
derived module name as literal segments — producing an illegal name because a segment cannot
start with a digit:

Investigated whether moditect's officially-supported mechanism for this (the <modules> list,
which lets you give OTHER artifacts an assigned name) could fix it. It cannot, at reasonable
spike scope:

  1. A shared/inherited <modules> list (in pluginManagement, applied to every module) backfires:
     moditect processes EVERY listed entry unconditionally on EVERY build using this plugin
     instance, regardless of relevance to the module actually being built. Adding zjsonpatch's
     mapping to the shared list caused kubernetes-model-core's (unrelated) build to fail trying
     to jdeps-analyze zjsonpatch in isolation, without zjsonpatch's own jackson dependencies
     available in that isolated invocation.
  2. Scoping the mapping down to a single, directly-relevant entry (kubernetes-model-common, for
     kubernetes-model-core) still fails: the <modules> list runs jdeps on kubernetes-model-common
     TOTALLY WITHOUT any of ITS OWN dependencies resolved (no jackson-databind, no slf4j-api) —
     the primary module's own resolved compile+runtime classpath is not shared with entries in
     this list.
  3. Explicitly replicating kubernetes-model-common's own transitive dependencies via each
     <module>'s <additionalDependencies> (jackson-databind, jackson-annotations, jackson-core,
     slf4j-api, each with an explicit <version>, since Maven property-managed versions are not
     inherited into this config either) DOES make moditect successfully generate a standalone
     descriptor for kubernetes-model-common as an independent side-artifact. But it does not fix
     the original build: kubernetes-model-core's OWN dependency-resolution pass for ITS OWN
     <module> (the primary artifact) is a SEPARATE code path that does not consult the <modules>
     list's assigned names at all — it re-derives kubernetes-model-common's name itself, hits
     the identical "999-SNAPSHOT" failure, and the build fails at the exact same point:

       [ERROR] Unable to derive module descriptor for
         .../kubernetes-model-common-999-SNAPSHOT.jar: kubernetes.model.common.999.SNAPSHOT:
         Invalid module name: '999' is not a Java identifier

  There is no supported moditect mechanism, within the add-module-info goal, to say "treat
  dependency X as module Y for the purpose of resolving MY OWN requires." The only way to make
  this work is for X to actually carry a real module-info in ~/.m2 — i.e. a fully-ordered
  `mvn install` across the whole affected dependency graph, which this task's constraints
  explicitly prohibit ("Do not add -am and do not run a full install"). Even if that constraint
  were lifted, it would only fix chains among modules THIS spike targets (kubernetes-model-core →
  openshift-model, kubernetes-client-api → kubernetes-client/httpclient-jdk); it would not fix
  kubernetes-client-api's ~20 non-target kubernetes-model-* siblings (gatewayapi, resource,
  rbac, admissionregistration, apps, autoscaling, apiextensions, batch, certificates,
  coordination, discovery, events, extensions, flowcontrol, networking, metrics, policy,
  scheduling, storageclass, node), none of which are ever given real module-info in this spike's
  scope and all of which carry the same "999-SNAPSHOT" version.

Contrast with the bnd arm (verified against its actual committed results, spike-results/
10-bnd-bundle-modules.txt and 11-bnd-packaging-gap.txt on branch spike/jpms-bnd): bnd ALSO could
not resolve kubernetes-model-core's real name for its dependents (it never got a correct one
either, and for kubernetes-model-core specifically bnd hit an unrelated NPE crash of its own).
bnd's generated `requires kubernetes-model-common transitive`, `requires kubernetes-model-core
transitive`, etc. use the raw, hyphenated Maven artifactId — objectively an equally WRONG module
name. But bnd's build did not fail on it. bnd's Import-Package-derived manifest generation is a
purely declarative, single-module analysis: it writes a `requires` clause referencing whatever
name it can guess, without ever validating that name against a real, resolvable module path.
jdeps is not declarative — `--generate-module-info` requires every jar it is given to already
resolve to a legally-named module (real or automatic) before it will run at all, or it refuses to
run for the whole invocation. This is the decisive structural difference this task exists to
surface: bnd fails soft (wrong name, non-fatal); moditect/jdeps fails hard (no output at all) on
the exact same underlying condition (999-SNAPSHOT dependency naming).

A provides clause IS present, with zero register:-equivalent configuration added anywhere in

## Summary of measurements requested by the task brief

1. Coverage across all 7 modules: NO — 1 of 7 (zjsonpatch only). The 3 packaging=jar modules
   (kubernetes-client-api, kubernetes-client, httpclient-jdk) all failed, so the claimed
   "moditect covers packaging=jar modules where bnd does not" advantage is NOT demonstrated by
   this run — the coverage gap here is worse than bnd's, not better, under the harness's exact
   constraints (see caveat below).
2. Per-module naming cost: 6 new <jpms.module.name> lines added (7th was pre-existing), vs bnd's
   5. At full 74-module scale: ~74 lines for moditect (minus whatever already carry one) vs 5 for
   bnd. But this undercounts the true cost for moditect: it additionally requires the ENTIRE
   non-target transitive dependency closure to resolve to a legal module name before jdeps will
   run at all — a cost with no bnd equivalent, and the actual reason 6 of 7 builds failed outright.
   + 1 central 13-artifact provided-scope exclusion list (pom.xml, shared pluginManagement
   configuration for the Sundr toolchain + lombok), no bnd equivalent, likely to recur as the
   closure widens — this is a direct reproduction of the split-package problem that made the
   rejected upstream PR (#7911) abandon generated descriptors in the first place, not a minor
   implementation detail. (Added by the Experiment A follow-up below; see there for the two
   distinct splits — io.sundr.model and io.sundr.builder — that made the single-artifact
   exclusion insufficient and forced the full 13-artifact list.)
3. Aggregator/skip cost: 0 poms needed <moditect.skip> — better than the brief anticipated.
4. Does moditect honour osgi.export: could not be tested — no descriptor was ever generated for
   the module pair in question. Structurally, jdeps's exports-from-physical-contents design means
   it cannot make the specific over-claiming mistake the bnd fix addressed, regardless.
5. provides for free: plausible and consistent with moditect's documented design, but not
   empirically confirmed in this codebase — the one module with a ServiceLoader provider
   (httpclient-jdk) never got a real moditect-generated descriptor either.

CAVEAT on finding 1: this specific coverage failure is a direct consequence of the interaction
between the harness's required methodology (`-pl <module>` without `-am`, no fresh `install`,
per this task's explicit constraints) and jdeps's strict module-path validation, compounded by
this project's "999-SNAPSHOT" dev-version convention. A full, dependency-ordered `mvn install`
would likely resolve the failures caused purely by OTHER TARGET modules lacking their own
freshly-generated descriptor (kubernetes-model-core → openshift-model/openshift-model-config,
kubernetes-client-api → kubernetes-client/httpclient-jdk) — this was not tested, since the task
explicitly prohibits `-am` and a full install, to keep ~/.m2 stable and comparable across arms.
It would NOT resolve the failures caused by genuinely out-of-scope siblings (kubernetes-model-
common, kubernetes-model-rbac, and ~20 more kubernetes-model-* artifacts kubernetes-client-api
depends on), since none of those are ever given a real module-info within this spike's 7-module
scope, and they carry the same "999-SNAPSHOT" version regardless of build order. Even under the
most favorable full-install scenario achievable within this spike's scope, moditect's coverage
of the 3 packaging=jar modules could not have been confirmed without ALSO naming ~20+ modules
that are explicitly out of scope for this task.

  uses io.fabric8.kubernetes.api.model.KubernetesResource

Two additional points fall out of this same evidence:
- **`requires io.fabric8.kubernetes.model.common` is objectively BETTER than what bnd produced**
  for the identical dependency edge in this exact codebase (bnd's own committed result,
  spike-results/10-bnd-bundle-modules.txt on spike/jpms-bnd, shows `requires
  kubernetes-model-core transitive` — the raw, hyphenated, wrong guess — because bnd never
  validates the name it writes). Once the closure resolves, moditect's requires are correct;
  bnd's can be silently wrong even when the build succeeds.
- **"provides for free" is now confirmed with a real, moditect-authored descriptor** (not the
  JPMS automatic-module-synthesis caveat noted in the original Step 10 write-up): `provides
  io.fabric8.kubernetes.api.model.KubernetesResource with ...` and `uses
  io.fabric8.kubernetes.api.model.KubernetesResource` were both generated with zero register:-
  equivalent configuration anywhere in this arm, directly from META-INF/services +
  addServiceUses. This is a genuine point in this arm's favor versus the bnd arm's Task 4
  register: work.

**What this does NOT show**: this is one dependency edge (kubernetes-model-core →
kubernetes-model-common), tested by installing exactly one extra, otherwise-out-of-scope module.
It is evidence that the closure-resolution mechanism itself works correctly once every jar in it
carries a real descriptor — not proof that all ~20 of kubernetes-client-api's out-of-scope
kubernetes-model-* dependencies would install cleanly at full 74-module rollout. Each one may
carry its own version of the Sundr split-package problem found here (most of them are generated
by the same kubernetes-model-generator parent and inherit the identical provided-scope Sundr
toolchain), and each would need the same 13-artifact exclusion list (or worse, if any has its own
distinct split). openshift-model-config, which depends only on kubernetes-model-core, was
re-tested unchanged and still fails exactly as before, because kubernetes-model-core itself was
only packaged, not installed, in this experiment (deliberately, to keep the experiment to the

So the corrected picture is: **the 1/7 slice-scoped result, as measured under this task's exact

correctly, edge by edge, once every dependency in the closure has a real descriptor; the real,
now-precisely-identified cost is that reaching that state requires resolving the same class of
Sundr split-package problem (found here, previously only hypothesized from the brief) potentially
many more times across the out-of-scope closure, at effort that scales with how many of that
closure's modules turn out to hit it.

## Follow-up: does moditect write into a packaging=jar main jar?

### The question

This arm's central claimed advantage over bnd is that moditect's add-module-info goal
post-processes a module's own main jar regardless of packaging, whereas bnd's descriptor lands in
a separate "-bundle" classified artifact for packaging=jar modules — so consumers depending on the
plain jar get nothing from bnd, but should get something from moditect. In the original Step 9
run, this was never actually measured: the only module that succeeded (zjsonpatch) is
packaging=bundle, and all three packaging=jar slice modules (kubernetes-client-api,
kubernetes-client, httpclient-jdk) failed on the jdeps closure-naming problem documented above,
for reasons unrelated to packaging. So the "reaches packaging=jar main jars" claim was an
inference from how the plugin is wired, not a direct measurement.

### Why generator-annotations

generator-annotations is packaging=jar and has zero compile-scope dependencies (its pom.xml has
no <dependencies> block at all — confirmed by reading the file directly). With no dependency
closure, there is nothing for jdeps to fail to resolve, and no confound with the 999-SNAPSHOT
naming problem that blocked every other packaging=jar module in this spike. This module is
explicitly outside the original 7-module slice; the coverage figures elsewhere in this file
("1 of 7", "6 new lines / 7 total") are unaffected by this section and do not include it.

Added to generator-annotations/pom.xml's (previously nonexistent) <properties> block:

  <jpms.module.name>io.fabric8.generator.annotations</jpms.module.name>
