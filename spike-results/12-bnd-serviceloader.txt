SYNTAX COST DATUM: the plain repeated-clause syntax (four separate
`osgi.serviceloader; osgi.serviceloader=...; register:=...` stanzas, each naming ONE
implementation, comma-separated in the same Provide-Capability property, exactly as
given in the task brief's Step 4 snippet) was sufficient. The `osgi.serviceloader~2`,
`~3`, `~4` duplicate-marker form was NOT required — bnd did not deduplicate the four
clauses down to one implementation in this case. Inspecting the raw manifest
(META-INF/MANIFEST.MF inside the bundle jar) confirms bnd preserved all four as
distinct Provide-Capability namespace entries:

Provide-Capability: osgi.service;objectClass:List<String>="io.fabric8.kubernetes.client.KubernetesClient,io.fabric8.kubernetes.client.NamespacedKubernetesClient";uses:="io.fabric8.kubernetes.client,io.fabric8.kubernetes.client",osgi.serviceloader;osgi.serviceloader="io.fabric8.kubernetes.client.ServiceToURLProvider";register:="io.fabric8.kubernetes.client.impl.URLFromEnvVarsImpl",osgi.serviceloader;osgi.serviceloader="io.fabric8.kubernetes.client.ServiceToURLProvider";register:="io.fabric8.kubernetes.client.impl.URLFromIngressImpl",osgi.serviceloader;osgi.serviceloader="io.fabric8.kubernetes.client.ServiceToURLProvider";register:="io.fabric8.kubernetes.client.impl.URLFromNodePortImpl",osgi.serviceloader;osgi.serviceloader="io.fabric8.kubernetes.client.ServiceToURLProvider";register:="io.fabric8.kubernetes.client.impl.URLFromClusterIPImpl"

(unwrapped from the manifest's 72-column continuation-line format for readability;
the header key/value content is otherwise verbatim)

`jar --describe-module` then merges these four same-namespace, same-interface
capabilities into the single `provides ... with a b c d` module-info entry shown above.
The brief's warned failure mode (dedup collapsing to one implementation, requiring the
`~2`/`~3`/`~4` marker) did NOT occur for this module/bnd version combination — recorded
here as a real (negative) cost datum for the comparison, not assumed.

No NPE occurred building kubernetes-client (its osgi.require-capability does not use
`filter:="(osgi.serviceloader=...)"`, so it does not hit the Task 2 bndlib NPE).

## Step 6: `uses` clause on the consuming side (kubernetes-client-api)

## uses clauses (derived from Require-Capability osgi.serviceloader)
NONE

kubernetes-client-api/pom.xml's current osgi.require-capability is:
    <osgi.require-capability>
      osgi.extender;
      filter:="(osgi.extender=osgi.serviceloader.processor)",
    </osgi.require-capability>
This names the generic serviceloader-processor extender, not a specific
`filter:="(osgi.serviceloader=<interface>)"` clause, so bnd has nothing to derive a
`uses` entry from. Building kubernetes-client-api (`./scripts/mvnj -pl
kubernetes-client-api package -DskipTests`) succeeded with no NPE — this module's
Require-Capability does not hit the Task 2 bndlib NPE pattern (no
filter:="(osgi.serviceloader=...)" present).

Per the brief: a missing `uses` does not break ServiceLoader resolution, but it is
required for jlink and is part of a correct descriptor. kubernetes-client-api would
need osgi.require-capability entries with filter:="(osgi.serviceloader=<interface>)"
for HttpClient$Factory and/or ServiceToURLProvider added to get a `uses` clause — this
task did not add that (out of scope per the brief; Step 6 is a check, not a fix).
Note: adding such a filter clause is exactly the shape that triggered the bndlib NPE in
kubernetes-model-core during Task 2 (see next paragraph) — this was NOT attempted here.

## NPE risk noted, not encountered in this task's builds

Task 2 found `JPMSModuleInfoPlugin.serviceLoaderUses` reads the serviceloader value via
plain `attrs.get(...)`, which is null when the value is expressed through
`filter:="(osgi.serviceloader=...)"`, causing an NPE at
`Descriptors.getTypeRefFromFQN` — this affects the `uses` path (serviceLoaderUses), not
the `provides` path (serviceLoaderProviders, which guards with containsKey and is
null-safe). None of the three builds run in this task (httpclient-jdk,
kubernetes-client, kubernetes-client-api) triggered this NPE, because none of their
Require-Capability blocks use the filter:="(osgi.serviceloader=...)" form. This risk
remains real for any module that does use that form (e.g. kubernetes-model-core per
Task 2) but was not re-triggered here.

## Scope note

This task proves a `provides` clause is emitted in the module descriptor for both
modules, and that the nested-interface and multi-implementation forms are emitted
correctly by bnd 6.3.1. It does NOT prove ServiceLoader resolves these providers at
runtime from a named module on the module path — that requires a module-path consumer,
which is out of scope for this task.
