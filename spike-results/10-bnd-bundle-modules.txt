## Edge case findings

### kubernetes-model-core build crash (blocks Step 7 for 1 of 4 modules)

`./scripts/mvnj -pl kubernetes-model-generator/kubernetes-model-core package -DskipTests`
fails with BUILD FAILURE. Stack trace (top frames):

  [ERROR] Bundle io.fabric8:kubernetes-model-core:bundle:999-SNAPSHOT : Exception: java.lang.NullPointerException: Cannot invoke "String.hashCode()" because "<local2>" is null
  	at aQute.bnd.osgi.Descriptors.getTypeRefFromFQN(Descriptors.java:703)
  	at aQute.bnd.osgi.Analyzer.getTypeRefFromFQN(Analyzer.java:3200)
  	at aQute.bnd.plugin.jpms.JPMSModuleInfoPlugin.lambda$serviceLoaderUses$35(JPMSModuleInfoPlugin.java:515)
  	...
  [ERROR] Bundle io.fabric8:kubernetes-model-core:bundle:999-SNAPSHOT : Verifier Plugin aQute.bnd.plugin.jpms.JPMSModuleInfoPlugin@326a6d81 failed Cannot invoke "String.hashCode()" because "<local2>" is null

Root cause, confirmed against the bndlib 6.3.1 source (bndtools/bnd JPMSModuleInfoPlugin.java,
serviceLoaderUses method):

  requireCapabilities.stream()
      .filterKey(key -> removeDuplicateMarker(key).equals(SERVICELOADER_NAMESPACE))
      .values()
      .forEachOrdered(attrs -> {
          TypeRef typeRef = analyzer.getTypeRefFromFQN(attrs.get(SERVICELOADER_NAMESPACE));
          ...
      });

This reads the `osgi.serviceloader` clause's own key ("osgi.serviceloader=<value>") as a plain
attribute. kubernetes-model-core's pom.xml (pre-existing, NOT modified by this task) declares:

  <osgi.require-capability>
    osgi.extender;
      filter:="(osgi.extender=osgi.serviceloader.processor)",
      osgi.serviceloader;
      filter:="(osgi.serviceloader=io.fabric8.kubernetes.api.model.KubernetesResource)";
      cardinality:=multiple
  </osgi.require-capability>

This is the spec-correct OSGi ServiceLoader Mediator form: a Require-Capability expresses the
value via an LDAP `filter:=` directive, not via a direct `osgi.serviceloader=<value>` attribute
(that direct-attribute form only applies to Provide-Capability, which kubernetes-model-core also
declares correctly and separately). bnd's serviceLoaderUses does not parse the filter string; it
does a naive attrs.get("osgi.serviceloader") lookup, gets null on this filter-only clause, and
passes null into getTypeRefFromFQN, which NPEs.

This is a genuine bug in bndlib 6.3.1 (embedded in maven-bundle-plugin 5.1.9), not a
misconfiguration on our side, and there is no `-jpms-module-info` instruction flag to disable
`uses` derivation from ServiceLoader capabilities (unlike the `requires()` method in the same
plugin, which honours an IGNORE_ATTRIBUTE that serviceLoaderUses does not check). The only ways
to avoid the crash — upgrading the pinned maven-bundle-plugin/bndlib version, or removing/altering
kubernetes-model-core's pre-existing osgi.require-capability — are both out of scope for this
task (central-version bump changes the comparison; per-module descriptor-content edits are the
exact thing this arm's thesis says not to touch). Left unfixed.

Consequence beyond kubernetes-model-core itself: because it never produces a jar with a real
Automatic-Module-Name/module-info, every module that depends on it (openshift-model,
openshift-model-config) can only guess its module name from the raw Maven artifactId
("kubernetes-model-core") rather than the correctly-dotted JPMS name
("io.fabric8.kubernetes.model.core") — see "dependency module names bnd had to guess" below.
This crash is squarely the subject Task 4 was scoped to investigate ("ServiceLoader provides
gap"), but it manifests as a hard build failure, not a soft gap.

build succeeds and the descriptor looks superficially correct.

## Harness fix (scripts/dump-module-descriptors.sh)

Found and fixed a latent bug in the "HAS module-info.class" branch, unrelated to this task's pom
changes but blocking faithful evidence collection: the original

  jar --describe-module --file="$jar" | { head -1; tail -n +2 | sed ... | sort; }

pipes the same command's output into both `head` and `tail` in sequence. `head -1` performs a
buffered read that drains the whole (short) pipe in one syscall, so `tail -n +2` sees EOF and
prints nothing — every "HAS module-info.class" block silently lost its exports/requires body,
keeping only the module-name header line. This never manifested in Task 1's baseline because no
jar there actually had a module-info.class (all 999-SNAPSHOT automatic-module names failed to
derive). Fixed by capturing the describe-module output into a variable once, then feeding that
same in-memory string to `head` and `tail` separately:

  mod_desc="$(jar --describe-module --file="$jar")"
  printf '%s\n' "$mod_desc" | head -1
  printf '%s\n' "$mod_desc" | tail -n +2 | sed 's/^[[:space:]]*//; s/[[:space:]]*$//' | sort

Verified fixed: the zjsonpatch dump in Step 7 above now shows exports/requires lines; before the
fix it showed only the module-name header line. This fix affects every later task that calls this
script; carry it forward.
